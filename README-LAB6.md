# TravelerAPI - laboratory 6: sharding

Application-level sharding of TravelerAPI over **16 virtual nodes** (`db_0..db_f`)
placed on **4 PostgreSQL services** (`postgres_00..postgres_03`), in the spirit of
Cassandra vnodes.

| Service       | Databases                 | Registry role |
|---------------|---------------------------|---------------|
| `postgres_00` | `db_0 db_1 db_2 db_3`     | publisher     |
| `postgres_01` | `db_4 db_5 db_6 db_7`     | subscriber    |
| `postgres_02` | `db_8 db_9 db_a db_b`     | subscriber    |
| `postgres_03` | `db_c db_d db_e db_f`     | subscriber    |

* **Shard key** - the last hex digit of the travel plan UUID.
* **IDs are generated by the API** (`crypto.randomUUID()`) before `INSERT`.
* **Co-location** - a location id ends with the same digit as its plan, so
  `PUT/DELETE /api/locations/:id` is routed without a lookup.
* **Mapping** - [`config/mapping.json`](config/mapping.json) (connection paths of all 16
  databases, credentials from `PG_USER`/`PG_PASSWORD`) or the shared registry
  database `shard_registry` (`MAPPING_SOURCE=registry`).
* **Connection pools** - one `pg.Pool` per database (`PG_POOL_PER_SHARD`, default 5),
  i.e. 20 connections per PostgreSQL service like the single pool of laboratory 4.
* `GET /api/travel-plans` is a scatter-gather over all 16 databases with a merge by
  `created_at DESC, id`.

Code: [`src/shards.js`](src/shards.js), [`src/app.js`](src/app.js),
[`docker-compose.lab6.yml`](docker-compose.lab6.yml), [`db/shard/`](db/shard).

## Run

```powershell
python scripts/lab6/bootstrap-env.py           # random local passwords in .env
python scripts/lab6/lab6.py up sharded         # 4 services, 16 databases, 2 API instances
python scripts/lab6/lab6.py seed sharded       # laboratory 2 dataset via shard-exec
python scripts/lab6/lab6.py hurl sharded       # 56 functional Hurl requests
bash scripts/lab6/run-suite.sh                 # every experiment of the report
```

APIs: `http://127.0.0.1:4567` and `http://127.0.0.1:4568`. Database ports are not
published; CLI tools run in the `tools` container inside the backend network.

## CLI: one script on all 16 databases

```powershell
docker compose -f docker-compose.lab6.yml --profile tools run --rm tools tools/shard-exec.js /sql/010_schema_migrations.sql [--dry-run]
```

[`tools/shard-exec.js`](tools/shard-exec.js): `BEGIN` + the whole file on every shard in
parallel, then `PREPARE TRANSACTION` on all 16 and only then `COMMIT PREPARED`.
Any failure rolls back all 16. `--recover <run-id> commit|rollback` finishes
transactions left in doubt. Scripts with their own `BEGIN/COMMIT`, `VACUUM`,
`CONCURRENTLY`, `CREATE DATABASE` are refused.

## CLI: rebalancing

```powershell
docker compose -f docker-compose.lab6.yml --profile tools run --rm tools tools/rebalance.js move db_3 postgres_03 [--drop-source]
docker compose -f docker-compose.lab6.yml --profile tools run --rm tools tools/rebalance.js status
```

[`tools/rebalance.js`](tools/rebalance.js):

1. creates `db_x` on the target, `PUBLICATION` on the source, `SUBSCRIPTION` on the target;
2. waits for `srsubstate = 'r'` on both tables;
3. `LOCK TABLE travel_plans, locations IN ACCESS EXCLUSIVE MODE` on the source, waits
   until the slot confirmed the lock LSN, compares row counts and MD5 of both copies;
4. drops the subscription (target becomes the writable master), restores the
   deferrable unique constraint, grants the API role;
5. bumps the version in `mapping.json` and `shard_registry` (and waits for the registry
   copies on `postgres_01..03`);
6. `REVOKE` on the old database and `COMMIT` (lock released);
7. the API receives `42501 insufficient_privilege`, re-reads the mapping and retries.

## Shared registry

`shard_registry` exists on every service. `postgres_00` publishes `registry_meta`,
`shard_map` and `shard_moves`; the other services subscribe. With
`MAPPING_SOURCE=registry` every API instance reads all copies and takes the highest
version.
